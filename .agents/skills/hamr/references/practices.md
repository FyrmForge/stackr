# HAMR Coding Practices

Conventions for writing Go handlers, `.templ` files, HTMX-driven UIs, and forms in a HAMR project. Violating these is usually the reason something "silently doesn't work" — especially with templ and HTMX.

---

## Go

### Package and file layout

- **One Go package per page**, with the directory tree mirroring the URL path:
  ```
  URL                     Package path
  /                       internal/web/handler/home/
  /login                  internal/web/handler/auth/login/
  /register               internal/web/handler/auth/register/
  /admin                  internal/web/handler/admin/
  /admin/users            internal/web/handler/admin/user/
  /admin/users/:id/edit   internal/web/handler/admin/user/edit/
  ```
  ```
  internal/web/handler/auth/login/
  ├── handler.go      // package login: NewHandler, Page, Submit, Logout, FormRules
  ├── login.templ     // package login: page templates
  └── login_templ.go  // generated by templ
  ```
- URL segments are typically plural; package names are singular Go identifiers (`/users` → package `user`).
- Parent directories without a page have no `handler.go` — they're just structural.
- A page package owns its handler, its templates, and any HTMX helper routes it needs (validation endpoints, partials, modals).
- **Pure-action endpoints (no view) live with the most related page.** `POST /logout` lives in `handler/auth/login/` because it's the inverse of login, not a page in its own right.
- **Section-shared web helpers live outside the handler tree.** Code used by multiple page packages in a section (e.g. session-cookie helpers shared by login + register) goes in `internal/auth/` (or similar). The handler tree stays a flat list of page packages.
- **Routes are wired centrally in `internal/web/server.go`.** Each page package contributes its page route plus every HTMX helper route it owns. Adding a new page = a new directory under `internal/web/handler/` plus a few lines in `server.go`.
- Shared templ components (layout, flash, nav, form helpers) live in `internal/web/components/`.
- Project middleware lives in `internal/middleware/`; framework middleware lives in `github.com/FyrmForge/hamr/pkg/middleware`.
- The repository pattern is used via a domain-local `Store` interface in `internal/repo/repo.go`. Handlers depend on the interface, not a concrete implementation — this keeps tests trivial.

### Functional options

Hamr packages use functional options consistently (`server.New`, `db.Connect`, `middleware.RateLimitWithConfig`, `websocket.NewHub`, etc.). Follow the same pattern when adding project-level constructors — variadic `...Option`, each option a function that mutates a config struct.

### Context

- Use `c.Request().Context()` to get the stdlib `context.Context` from an Echo `c`.
- Never put arbitrary values in the request context with raw string keys — use `pkg/ctx.NewKey[T](name)`.
- When logging from a handler, resolve the logger from the request context: `logging.FromContext(c.Request().Context())`. Don't pass around a package-level logger.

### Error handling

- Return errors up from handlers — the framework's error-page middleware (`middleware.ErrorPages`) will render them as HTML (or JSON for API routes).
- For expected validation errors in forms, use `validate.Form.Validate(c)` — do **not** return a plain error.

### Config

- Read env via `pkg/config` (`GetEnvOrDefault`, `GetEnvOrPanic`, `GetEnvOrDefaultInt`, `GetEnvOrDefaultBool`, `GetEnvOrDefaultDuration`).
- Required values at startup should use `GetEnvOrPanic` so misconfiguration fails fast.
- Load `.env` via hamr (automatic for the CLI) or Go's own env handling; don't re-invent it.

### DB

- Query via `sqlx` (or `gorm` if scaffolded with `--db-connector gorm`). Always pass the request context to the DB driver.
- Migrations live in `internal/db/migrations/` as numbered `*.sql` files. `hamr dev` runs them on start (when `--migrate-startup` was used at scaffold time) or you run `make migrate` manually.
- The scaffolded `internal/db/db.go` embeds `migrations/*.sql` — when adding a migration, just add the `.sql` file; the embed picks it up at build.

### Logging

- `logging.New(production bool)` at startup.
- `logging.WithLogger(ctx, l)` to stash it; `logging.FromContext(ctx)` to retrieve. Middleware already wires this plus request ID, locale, and subject ID.
- `logging.With(ctx, "key", value, ...)` attaches fields to the contextual logger.

## templ

### The non-negotiables

1. **`.templ` is NOT `html/template`.** It is compiled to Go. After editing a `.templ`, the matching `_templ.go` must be regenerated. `hamr dev` / `make build` do this for you; if you're editing files and calling `go test` manually, run `templ generate` first.
2. **Inline control flow cannot have HTML bodies.** This compiles but is silently dropped:
   ```templ
   templ Bad() {
     if cond { <p>dropped!</p> }   // SILENT — linter catches as `inline-if`
   }
   ```
   Use block form:
   ```templ
   templ Good() {
     if cond {
       <p>shown</p>
     }
   }
   ```
   Same rule applies to `for` and `switch`. `hamr lint templ` / `make templint` enforces this.
3. **Interpolate Go expressions with `{ expr }`**, not `{{ ... }}`. Templ compiles `{ user.Name }` into a call to a Go function.
4. **Component composition uses `@Component(...)`**, children blocks use `{ children... }`.

### Layout pattern

```templ
templ Layout(title string) {
    <!DOCTYPE html>
    <html>
        <head>
            <title>{ title }</title>
            <link rel="stylesheet" href={ StaticURL("css/app.css") }/>
            <script src={ StaticURL("js/htmx.min.js") } defer></script>
        </head>
        <body>
            { children... }
        </body>
    </html>
}

templ HomePage(user *models.User) {
    @Layout("Home") {
        <h1>Welcome, { user.Name }</h1>
    }
}
```

### Static asset URLs

- Call `StaticURL("css/app.css")`, not a hardcoded path. The helper resolves to a fingerprinted path in production (`css/app.a1b2c3d4e5f6.css`) and the raw path in dev.
- Never reference anything under `frontend/dist/` directly — that dir is generated.

### Accessibility + hygiene

- Every `<img>` needs `alt`. Every `<a>` needs `href`. The templ linter (`hamr lint templ`) will flag both.
- Avoid inline `style=""` — use CSS classes. Avoid `class=""` empty attributes.

## HTMX

HAMR is HTMX-first. Handlers return HTML fragments; HTMX swaps them into the DOM. You should rarely write client-side JS for interactions that could be server-rendered.

### Partial vs full render

Every "this page can be hit directly or loaded via HTMX" handler follows the same shape:

```go
func (h *Handler) UserList(c echo.Context) error {
    users, err := h.store.List(c.Request().Context())
    if err != nil {
        return err
    }
    if htmx.IsHTMX(c.Request()) {
        return respond.HTML(c, http.StatusOK, templates.UserTable(users))
    }
    return respond.HTML(c, http.StatusOK, templates.UserListPage(users))
}
```

- `*Page` templ components wrap `@Layout(...)`.
- Partial (`UserTable`) is the same fragment rendered inside the page for direct hits.

### Redirects

- Handler-side: `respond.Redirect(c, url)` — HTMX requests get `HX-Redirect`; others get 303.
- Response-header-only: `htmx.Redirect(c.Response(), url)` when you specifically need HTMX behaviour.

### Events

- Server-fired client events: `htmx.Trigger(c.Response(), "userCreated", "showToast")`.
- Timing variants: `htmx.TriggerAfterSettle(...)`, `htmx.TriggerAfterSwap(...)`.

### Swap and target overrides

- `htmx.Reswap(c.Response(), "outerHTML")` — change swap mode from the server.
- `htmx.Retarget(c.Response(), "#error-box")` — change target from the server.
- `htmx.PushURL(...)`, `htmx.ReplaceURL(...)` — URL bar control.

### OOB swaps

Out-of-band swaps let a single response update multiple DOM regions. Any returned element with `hx-swap-oob="true"` replaces the element with the matching ID anywhere on the page, independent of the main swap target.

```templ
templ CreateUserResult(u User) {
    <tr id={ "user-" + u.ID }>...</tr>                  // main target swap
    <span id="user-count" hx-swap-oob="true">{ strconv.Itoa(newCount) }</span>  // OOB
}
```

Use OOB swaps for: flash messages, counter badges, inline form field errors, sidebar state updates.

### Forms + validation

1. Prefer `validate.NewForm(...)` + `validate.Field(name, rules...)`.
2. Call `form.ValidationHandler("field")` to wire an inline HTMX validation endpoint — triggered by `hx-post` on field `blur`/`change`.
3. On submit, call `form.Validate(c)`; if errors, re-render the form partial with `map[string]string` of errors (the form renderer will place them next to fields and send OOB swaps if you configure `WithOOBRenderer`).

### PRG

POST handlers that succeed **must** redirect (don't render the result page directly):

```go
if err := h.store.Create(ctx, in); err != nil {
    return err
}
return respond.Redirect(c, "/users/" + in.ID)
```

This prevents form resubmission on refresh and plays nicely with HTMX's `HX-Redirect`.

## Forms

A canonical form flow in HAMR:

1. Define the form in a handler-adjacent `forms.go`:
   ```go
   var EditUser = validate.NewForm(
       validate.Field("name", validate.Required, validate.MinLen(2)),
       validate.Field("email", validate.Required, validate.Email),
       validate.FieldMsg("age", "Must be 13+", validate.AgeMin(13)),
   )
   ```
2. Wire the inline validation route:
   ```go
   e.POST("/users/validate/:field", EditUser.ValidationHandler("field"))
   ```
3. In the templ form, call each field via the form's renderer so errors surface consistently.
4. On submit:
   ```go
   errors := EditUser.Validate(c)
   if len(errors) > 0 {
       return respond.HTML(c, http.StatusOK, templates.EditUserForm(in, errors))
   }
   // ... persist ...
   return respond.Redirect(c, "/users/" + in.ID)
   ```

## Testing

- Unit tests live next to the code they test (`_test.go`), using the standard `testing` package.
- Handlers are tested against the `Store` interface — swap in a fake or in-memory implementation.
- E2E tests (when scaffolded with `--e2e`) use `pkg/e2e` (go-rod). Prefer the HTMX-aware helpers (`WaitForHTMXIdle`, `ClickAndWaitHTMX`) over raw sleeps.
- Never run `go test ./pkg/foo` directly — go through `make test` so templ generation and locale generation run first.

## Linting

- `make lint` runs `golangci-lint` with project config.
- `make templint` runs `hamr lint templ` across `.templ` files.
- Before declaring a change done in a scaffolded HAMR project, run the relevant Makefile targets explicitly: `make build`, `make test`, `make lint`, and `make templint`.

## hamr MCP

When `[dev.mcp]` is enabled in `hamr.toml`, a running `hamr dev` exposes its
state as MCP tools. Prefer them over the manual equivalent — they read the live
server, so the answer is current and costs the developer nothing. Exactly which
tools exist depends on `[dev.mcp.access]`; `hamr setup` writes a project-specific
version of this list into `AGENTS.md` and `CLAUDE.md`.

- `logs.read`, `console.read`, `http.read` — app/build output, browser console
  (uncaught errors, CSP violations), and the HTTP request log. Never ask the
  developer to paste logs.
- `rule.run`, `rebuild.all`, `make.run` — the dev server is already running;
  never start a second one or shell out to `make build`.
- `docker.status`, `docker.logs` (+ `docker.restart`, `docker.wipe` at write) —
  check dependency containers before blaming the app for a connection error.
- `mail.list`, `mail.get` (+ `mail.clear`, `mail.ingest`) — read the dev inbox
  instead of asking what an email said.
- `stripe.list` (+ `stripe.complete`, `stripe.expire`, `stripe.refund`) — read
  and drive the Stripe mock instead of guessing at payment state.
- `dev.info` — running rules, ports (including walked ones), versions.

A call failing with "dev not running / gateway off" means `hamr dev` isn't up or
the gateway is off — say so rather than silently falling back to manual steps.

## What NOT to do

- **Don't render HTML outside `respond.HTML`.** It breaks error-page middleware and HTMX/full-render branching.
- **Don't use `html/template`.** Templ is the framework templating layer; mixing engines fragments the build.
- **Don't add new frontend JS libraries without `hamr vendor`.** Vendored assets are version-pinned, checksum-tracked, and committed under `frontend/static/js/`.
- **Don't hand-write fingerprinted filenames.** Use `StaticURL(...)`; the manifest is generated.
- **Don't use `c.Get("userID")` style untyped keys.** Use `pkg/ctx.NewKey[T]`.
- **Don't call `go build`/`go test` on single packages.** Always `make build` / `make test`.
- **Don't do by hand what the hamr MCP tools do.** Reading logs, rebuilding, checking containers, and inspecting the mail/Stripe mocks all have tools when `[dev.mcp]` is enabled — see [hamr MCP](#hamr-mcp).
- **Don't write inline `if`/`for`/`switch` with HTML bodies in templ.** They compile but produce nothing.
- **Don't commit `.env`, `**/node_modules/`, or `.hamr/`.** All gitignored by scaffold. `frontend/dist/` *is* committed — the fingerprinted manifest is compiled into the binary, so the build needs it.
