## Bugs found

No product bug. All failures were in the script, all fixed in `scripts/qa/blitz.sh`:

1. Caddy upstream containers on `--network host` clashed with the proxy's admin port 2019; added `admin off` to both Caddyfiles (route, fwdauth).
2. The qa stack/env were only made when `login` ran; the stack setup now always runs. `env create` needed `--from-kind branch --from-branch main` for a first env.
3. Cleanup left the stack behind (`env rm` missing, tile removal was async so share/env removal raced it); now tiles go first, synchronously, then share, grant, env, stack.
4. `tile exec` forwards stdin and waited forever without EOF; every call now has `</dev/null`; the exec error is no longer swallowed.
5. A fresh NFSv4 server blocks writes for its 90s grace period; the wait is now 95s.
6. share-managed-refused grepped for "share"; the product refuses earlier with "managed tiles do not take volumes", so the check accepts either.
7. files check: files-plain passed on any output (even an error); it now compares the exact content. It also pushes a commit via `gh api` to create release 1 before `promote 1`.

## Not fixed, worth a look

- Removing a share leaves its Docker volumes (`stackr-share-<id>-<hash>`) on the host, one per share and sub path. The leftovers from this QA (and a bare volume named `share`) are still on the rig: my cleanup of them was blocked, so they need a manual `docker volume rm`. Product question: should `share rm` prune them?
- FyrmForge/stackr-qa-blitz could not be deleted (gh token lacks the delete_repo scope). It is private and throwaway: delete it by hand.
