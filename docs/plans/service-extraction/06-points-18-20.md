# Point 18 — one authorization path

## The insight that shrinks this

The auth layer does not need a tile. It needs the ORG a request is about,
and then the user's standing in it. It never touches config or state.

Where the org comes from differs per surface:

  API   addresses by slug path: org_a:stack_b:env_c:tile_d
        -> the org is IN the request. Zero reads.

  panel addresses by opaque id: /apps/:id, /projects/:id, /envs/:id
        -> the org is nowhere in the request. One lookup needed.

That lookup is the ONLY read authorization requires:

    // id -> the org that owns it. One field. Not the row.
    TenancyOf(ctx, kind, id) (orgID string, err error)

This is why the 35 gate helpers exist. Not because auth wants the resource —
because the URL will not say which org it is in. Give auth a resolver and the
helpers have no reason to be.

## Shape

  Domain services   reads + writes. No principal, no auth. The janitor, the
                    work queue and the config apply use them as-is.
  Resolver          TenancyOf. The one read auth makes.
  Route table       declares the verb beside the route.
  AccessService     owns what the verb needs. Already built (point 15).

    site.POST("/projects/:id/settings", projectHandler.SaveSettings,
        auth.RequireAuth(), requireVerb(service.VerbStackWrite))

Gate on the ROUTE, not in the handler body: the body is where forgetting
happens. On the route the level is visible where the route is declared, a
route with no verb is a missing entry you can grep, and a test can walk
Echo's registered routes and fail any mutating route with no verb.

REJECTED: gating inside the service read (tiles.Get(ctx, principal, id)).
Bakes authorization into the orchestrator and forces background readers to
carry a fake principal.

## Order of work

1. The route-verb test FIRST, alone. It fails against today's code, and that
   failure list IS the inventory of what the helpers silently enforce.
   Rationale: a missed read is a compile error, a missed gate is silent.
2. TenancyOf resolver + verbs on every route.
3. Delete the gate helpers.

## Surface error policy — DO NOT FLATTEN

  panel  tenancy/owner refusals answer 404  (a 403 confirms the id exists)
  api    the same refusals answer 403

AccessService already returns ErrNotFound vs ErrForbidden. The HTTP mapping
stays per surface. Flattening these leaks exactly what the 404 hides.

# Point 19 — services own their reads

## Measured state

Read methods per service: tile 0/11, stack 0/8, environment 0/7, deploy 0/6,
domain 0/8, variable 0/11, managedinstance 0/13, slice 1/13.

Handlers -> store direct reads: 411 sites, 77 distinct store methods.
Worst file: project/handler.go, 76 store calls.

Top: GetOrgBySlug 31, GetOrg 28, ListEnvironmentsByStack 24, GetStack 24,
GetEnvironment 23, GetTile 22, ListVariables 21, ListTilesByEnv 17.

Points 1-17 extracted writes only. Never stated as the scope; it happened
because every point was chasing a behaviour bug and those live in writes.

## Why it matters beyond tidiness

Reads scattered across handlers are how the two surfaces drifted in the first
place. The same question gets asked two ways:
  - a tile is addressable by id or by org:stack:env:tile. API has
    tileByPath/stackByPath/orgByPath/envByPath; the panel has 13 slug
    lookups of its own.
  - BackupDestinationService.Visible (an org's own buckets plus shared ones)
    was written out three times before it moved.
  - VariableService.Masked — a secret reads as ••• in any listing the caller
    may not see plaintext in. Wrong once = a leaked secret.

## Open question for the dev

Q. Pass-throughs. h.store.GetOrg(ctx, id) -> h.orgs.Get(ctx, id) enforces no
   rule; it is indirection for its own sake. Do those move too (uniform, one
   door, easy to state) or stay (less churn, but two rules for where a read
   lives)?

Dev has said: reads must not be scattered. Reading that as "they move too" —
CONFIRM before building.

## DECIDED: two readers per thing, split on cost not on kind

Not config-vs-state. Every orchestrator puts declared and last-known-observed
in ONE read:
  k8s    GET /pods/y -> spec AND status together. The /status subresource is
         a separate WRITE path (controllers write status, users write spec);
         reading it still returns the whole object.
  swarm  service inspect -> Spec + ServiceStatus + UpdateStatus, one doc.
  nomad  the job object carries its own Status field.

What they DO split out is expensive/live/can-be-absent:
  k8s    kubectl top -> metrics.k8s.io, a different API server entirely
  swarm  service ps (tasks), stats (streaming)
  nomad  job allocations

So the line is cheap+stored vs expensive+live:

    tiles.Get(ctx, id)               // row: config + recorded status.
                                     // cheap, always works.
    tiles.Live(ctx, id)              // docker: container state, replicas.
                                     // slow, can fail, node can be down.
    tiles.Metrics(ctx, id, window)

Load-bearing, not cosmetic: the healthy-tile-reads-"Crashed" bug (3a268e0)
was a page with both available picking the wrong one. Two named calls force
the caller to say which it is rendering.

## DECIDED: Live is a BULK read. The tree call is the primitive.

Not N per-tile docker calls. One TaskList against the manager, sliced.

The primitive already exists and is already used:

    runtime.RunningTileTasks(ctx)   swarm.go:295
      -> one cli.TaskList with desired-state=running
      -> map[tileID]NodeTask, keyed off the stackr.app / stackr.db label
    runtime.TasksByNode(ctx)        swarm.go:328  same shape, for counts

So the service layer gets:

    env.Live(ctx, envID)        one TaskList, sliced to this env's tiles
    stack.Live(ctx, stackID)
    org.Live(ctx, orgID)
    tiles.Live(ctx, id)         DERIVED from the bulk call, not the reverse

This is what k8s and swarm both do: LIST with a selector, never GET in a
loop. kubectl get pods -n foo is one request.

Build order matters: bulk first, per-tile derived from it. Per-tile first
and "add bulk later" leaves you with both, and the loop survives.

Consequence: the bounded-concurrency worry from the 20-tiles case largely
goes away. A tree read is ONE call to the manager.

### The half that does not bulk — a limit, not a choice

TaskList answers for the SWARM. Anything that is not a swarm task still needs
a per-node call:
  - plain containers on a node (the containers screen)
  - volumes on disk (ListVolumes, node Remove modal)
  - exec, terminal, file browse
These already route through cluster with its own timeouts. So Live has a
fast bulk half and a slow per-node half, and that seam is imposed by docker.

For the per-node half only, the earlier requirements still stand:
  - bounded concurrency (precedent: cron_run_concurrency,
    backup_run_concurrency, volume_move_concurrency are already settings)
  - partial results render; a node that did not answer shows unknown
  - one unreachable node must not stall the page
Existing precedent for degrading: the node Remove modal renders with a
message when its volume listing times out, because the node being removed is
often the one already gone. components.PageCtx (5s) is the existing bound.

## Deferred, deliberately

The GetConfig()/GetState() split as SEPARATE READS. Superseded by the cost-based split above.

What survives from it and is still worth doing: separating the WRITE paths,
which is what k8s actually enforces with the /status subresource.

    tiles.Update(...)      // config only. user-driven; config-as-code owns it
    tiles.SetStatus(...)   // state only. deploy engine and workers own it

Evidence it is needed: ManagedInstanceService.Deploy exists because
"deploy, then write a status, then tell the canvas" was hand-copied to six
call sites and the image watcher wrote no status at all. Separating the write
paths also makes point 13's managed gate structural instead of conventional —
config-as-code writes the config path and is unable to reach the state path.

Blocked on: repo.Tile is one struct holding both (GitURL/ImageRef/Volumes
next to Status/ImageDigest/HomeNode/LatestDigest). Model split, not a read
refactor.

# Point 18's safety net — landed

`internal/stackrd/handlers/web/routeverb_test.go`
(`TestEveryMutatingRouteNamesAVerb`).

It builds both surfaces onto one Echo, walks every registered route, and fails
any mutating one (POST/PUT/PATCH/DELETE) that names no `service.Verb`.

**How a route names its verb.** Echo already carries a `Name` per route,
defaulted to the handler's function name, so the declaration needs nothing
built to hold it:

    site.POST("/projects/:id/settings", h.SaveSettings).Name = string(service.VerbStackWrite)

and point 18's `requireVerb` middleware reads the same field. This is a
change from the shape sketched above — the sketch passed the verb as a
middleware argument, which the middleware still can, but the *declaration*
has to live somewhere a route walk can see it, and Echo's own field is that
somewhere.

## Three buckets, not two

The walk skips two kinds of route, and which bucket a route is in is the
first decision point 18 makes about it.

**Unauthenticated (14).** They carry their own credential and answer before
there is a principal: `/login`, `/login/validate/:field`, `/logout`,
`/register`, `/register/validate/:field`, `/invite/:token` (the invite token),
`/s/:token` (the share link), `/hooks/github/:stack` and
`/hooks/connectors/:id` (signatures), `/join/:key/node` (the node join key),
`/cli/exchange` (the pre-auth half of the CLI login). `/api/v1/nodes/samples`
belongs here too and is not in the walk — it registers only when the node
service is wired.

**Personal (8).** Authenticated, but not org-rooted: `/account/*`,
`/notifications/*`, `/orgs/switch`, `/cli/authorize`. They write the signed-in
user's own row. The verb table is org-rooted by design, so there is no verb to
name — what gates these is "it is yours", which is the session subject.

**OPEN QUESTION for the dev.** Do the personal routes stay outside the table,
or does the ladder grow a rung meaning "self"? Leaving them out means the
route walk can never answer for them, which is the same "a test cannot see it"
problem point 18 exists to remove — but a self rung is a rung that is not a
comparison against an org, and the whole point of `Level` is that a check is a
comparison. Left as it is for now, and named in `personal()` so it is a list
somebody has to edit rather than a silence.

**Owes a verb: 271.** Every one of these has its level decided today inside a
handler body or a gate helper. None of them is a route that should be open.

## What the test does NOT do

It does not check that the verb is the *right* one. A route that names
`VerbOrgRead` for a write passes. What point 15's table gives is that a wrong
verb is at least a written-down wrong verb, which is the thing the two gate
vocabularies never were.

Nothing was deleted. No gate helper was touched.

# Point 19 — the blocking question, answered 2026-09-19

**Pass-through reads move too.** `h.store.GetOrg(ctx, id)` becomes
`h.orgs.Get(ctx, id)` even where the service method enforces nothing. One rule
for where a read lives, and it is greppable: no `h.store.` in a handler.

**Handlers lose the store; they KEEP `repo.X` as their view type.** The dev's
reason for the rule was behaviour — "so they don't do anything that should be
done in a uniform way as a service" — and banning the store call buys all of
it. A handler holding a `repo.Tile` struct can do nothing with it; it has no
store to do it against.

Banning the `repo` import outright was considered and rejected for now: 150
handler files and 39 `.templ` views are TYPED on those structs (317 references
to `repo.Tile` alone), so removing the import is a type migration across the
whole panel, not a read refactor. It is also point 20's blocker arriving
early, since `repo.Tile` is exactly what point 20 needs split. Type aliases
were rejected as cosmetic.

**One misfiled function to move on the way:** `MetricPoints` lives in

# The four open decisions — decided 2026-09-19

The dev delegated these. Reasoning recorded so they can be overruled on sight.

## 1. The org-domain asymmetry → BOTH become owner

`POST /orgs/:slug/settings/domains` is write today, `.../domains/delete` is
owner. Align UP, not down.

Points 7, 10 and 11 already set the precedent for exactly this shape: where
the two surfaces disagreed about a level, the lower one was never a considered
grant, it was a forgotten guard, and the higher level wins. Same reasoning
applies to one surface disagreeing with itself.

Loosening delete to write would be a security change made to remove an
inconsistency, which is the wrong direction to resolve one. An org domain is
org-level routing: a member adding a host that squats a name is not obviously
less impactful than removing one.

Change: `POST /orgs/:slug/settings/domains` moves `VerbDomainWrite` ->
`VerbOrgWrite`, and the row in `routelevel_test.go` gets edited to `owner`
with this section named as what decided it.

WATCH FOR: this takes the ability to add an org domain away from members. If
that breaks a real workflow, the answer is a dedicated owner-level verb for
domains rather than dropping delete to write.

## 2. Scope grants at mint time → bind NEW keys, leave existing ones

The hole: scopes are granted against whichever org the minting browser's
cookie pointed at, and a key carries no org of its own, so write scopes minted
on org A travel to org B. Today the live role check in the target org is the
only thing stopping it.

Decision: an API key records the org it was minted for, and its scopes are
checked against that org. Existing keys have no org; a NULL org keeps today's
behaviour (scopes valid in any org the user belongs to).

Not a retroactive narrowing, deliberately. Silently shrinking what a live
credential can do breaks running CI with no signal to its owner, and the role
check already bounds the damage — this is defence in depth, not the only
defence. New keys are bound from the day it ships; old ones are visible in
the panel and can be rotated.

This is the one decision here with blast radius outside the repo. If it should
be retroactive, that is a deliberate, announced revocation, not a refactor.

## 3. Deactivation should revoke share links → YES

Demotion, removal and a stack move all tear down the share links the person
minted (RevokeService, point 15). Deactivation does not, which makes it the
weakest of the four — a deactivated user's drop boxes keep answering at `/s/`
with no role check anywhere on that path.

Change: the deactivate path calls `RevokeService`, matching links by
`CreatedBy`, exactly as `MembershipChanged` does. Small, and it closes the
last bearer-token hole point 15 opened.

## 4. What is next → GATE THE READS, then point 19

Reads first:
  - it finishes point 18 rather than leaving it half-applied, and empties
    `stillBodyGated`, which is 162 handlers currently carrying a second check
  - it is the smaller job (192 routes, and the machinery exists)
  - point 19 is cleaner afterwards, because handlers stop juggling two
    authorization shapes while their reads are being moved

Then 19, then point 20's embedding (which 19's handler churn should precede).

Carry into it the caveat already written down: the level capture is WEAKER for
reads, because for a read-only handler the gate helper IS the body check, so
deriving levels from the helpers and deleting them is more circular than it
was for writes. Read the owner-level pages by hand rather than trusting the
walk — the failure is a settings page that reads as read-level.

# Point 18, finished — the reads, 2026-09-20

The 192 GET routes are gated. Point 18 is complete: every route on both
surfaces either names a verb or says, in a list with a reason next to it, why
it cannot.

## What "cannot" means

Three shapes, and none of them is unfinished work:

- **Collections.** A listing spans orgs, so there is no single tenancy to
  resolve before the handler and the check is a per-row filter inside it. Ten
  routes: the API's /apps, /dbs, /stacks, /orgs, /domain-resources and
  /backup-destinations, and the panel's home canvas, its status poll, search
  and the legacy /settings redirect. Stripping these would show every user
  every row.
- **Deferred.** The org arrives with the request rather than in the path. The
  five KindDeferred routes, plus the GitHub App callback, whose opaque state
  token IS the credential.
- **Public.** Health, the OpenAPI document, avatars, the registry token
  endpoint and the websocket, which authenticate themselves or are public by
  design.

They are listed in handlers/web/routeread_test.go, and a new GET that is in
neither list fails that test.

## Decisions taken while doing it

**5. Org config-as-code plans are owner-level on both surfaces.** The panel
required an owner to list or view them (ownedSettingsOrg); the API let any
member list them. Two surfaces, one operation, the higher level wins — points
7, 10 and 11 again. VerbOrgPlanList, which named the read half of that
disagreement and was never wired to a route, is gone; VerbOrgOwnerRead covers
every owner-level org read, which is the invite list, the org's plans, the
setup wizard and the wizard's repo picker.

**6. An owner-only PAGE answers 404 on the panel, not 403.** The helpers it
replaces answered "org not found" to a member, deliberately: an invite list,
an org's plans and a half-built org are not things a member should learn
exist. Writes keep the 403 — the caller already knows the org and asked to act
in it. The API answers 403 for both, and that split stays.

**7. Revealing a secret VALUE over the API needs write in the org, not just
the scope.** secrets:read is a write-grade scope, so only someone with
content-write can mint it — but a key outlives the role that minted it, and
the routes it rides on are read-level. A member who minted a key and was then
demoted to viewer kept reading every secret in the org. The panel already
asked for write on both the reveal and the Copy endpoint; the API now does the
same, checked live, per request.

**8. Four "reveal this variable's value" GETs are write-level reads**, on both
surfaces, because that is what the panel already enforced by hand. They carry
VerbVariableWrite. So does /api/v1/tiles/:id/forward, which opens a tunnel
into the container and said so in a comment.

## A regression this found

Gating the backup reads surfaced one the WRITE phase introduced and no test
caught: the panel's own database backup belongs to no org, TenancyOf answered
"" for it, and "" is how the gate spells "no such thing", so every gated
backup route 404'd the admins it was for. TenancyOf now answers
service.ErrServerOwned for it and both gates translate that into admin-only.

check. A move edits two orgs: the route's gate answers for the org the stack
is leaving, and the org it moves into arrives in the form. Restored, and the
handler is on stillBodyGated with the reason. That list is now what must keep
a body check, not a worklist.
