# Shard g: boot and background workers (lens 2, call sites)

Everything that runs outside a request handler: `cmd/stackrd/main.go` boot sequence, `cmd/stackrd/seed.go`, and the tickers, janitor tasks, cron entries and workqueue consumers under `internal/stackrd/infra/`. Rows are call sites. Paths under `internal/stackrd/` unless noted. Read-only sweep, 2026-09-18. Does not repeat what `x-deploy-orchestration.md` (engine call sites), `x-notifier-mail-scheduler.md` (Push and nudges from workers, `LoadSchedules` at boot) or `x-proxy.md` already row.

Question answered here: which worker or boot step touches store and infra together (a service in disguise), which re-implements a rule a handler also has, and which writes a row a handler also writes.

Legend, "agrees?": Y = same impl or same rule; N = different rule or missing step; -- = no handler twin (worker-only). "class" as in `01-discovery.md`; "svc" = no drift, but store+infra together, so it is a service candidate.

## 2. Findings

F1. [A] Boot legacy-mount conversion is a third "create volume tile" writer with its own rules. `envops.go:642-700` creates volume tiles with `uniqueSlug`, no `ConfigManaged` gate, no redeploy of the attached app; web `project/handler.go:603-616` gates on `ConfigManaged` and enqueues `"volume"`, api `volumes.go:55-81` enqueues. One-shot, so low blast radius, but it is the same operation under a fourth rule set.

F2. [B] Boot never renders the managed registry's traefik route. `main.go:286` runs `EnsureManaged`, which creates the row and the service but not `registry.yml`; `px.Resync` `proxy.go:577-624` regenerates app routes, custom entries and stack middlewares only. `WriteRegistry` is called from `web/settings/handler.go:624` and `api/registry.go:319` alone. The comment at `proxy.go:715` lists `registry.yml` as a hand-managed file, so a wiped data dir heals everything except the registry route.

F3. [A] Two answers for "this deploy did not finish". `SweepStaleRuns` `sqlite/deployments.go:57-59` writes `error` + `InterruptedMsg` and moves `building` tiles to `stopped`; a user cancel via `engine.Cancel` `engine.go:313` writes `cancelled`, and the engine finish path writes tile `stopped` on cancel but `error` on failure `engine.go:497-510`. `waiting_ci` rows are not swept at boot, so `cigate` picks them up again (`cigate.go:40`), which is probably intended but not stated anywhere. Same split in the queue: restart closes a cron run as `error`/`interrupted` (`jobs.go:227`), a user stop closes it as `stopped` (`jobs.go:249-252`).

F4. [A] Trusted proxy CIDRs have two validation policies. `seed.go:54-57` skips an unparsable CIDR with a warning and keeps going; `web/settings/proxy.go:74-77` rejects the whole save with 400. Cloudflare: seed leaves the box off on fetch failure (`:67`), handler falls back to `cloudflare_cidrs` cache and only 502s when the cache is empty (`:83-89`). No API writer for either setting (grep `trusted_proxies` in `api/v1` empty).

F5. [A] `tiles.image_digest` has three writers with three triggers. `main.go:420-424` (engine `OnFinish`, only `SourceType=="image"` and `done`), `managedtiles.go:497-500` (every managed `Deploy`), `imagewatch/watcher.go:118-127,183-187` (first sight with empty digest; after auto-update on the managed and cron branches). The watcher's cron branch (`:163-173`) pulls and re-baselines, but a cron that later gets rebuilt by the engine never re-baselines because its `SourceType` is `image` only when it is not a git build (not checked whether cron tiles can be git-sourced).

F6. [A] Image auto-update bypasses the upper-env deploy gate. `watcher.go:175` calls `Engine.Enqueue` with no `envnet.UpperEnv` check; web `deployment/handler.go:81` and api `apps.go:485` both refuse a manual deploy in an upper env with 400. `EnqueuePromote` is the sanctioned path there (`apply.go:141`). A tile in an upper env with `update_policy=auto` is the one tile that can be redeployed from outside a promotion.

F7. [B] Managed-instance auto-update writes no status. `watcher.go:152-162` runs `DB.Deploy` on `context.Background()` and records only a `watch:` cron run on failure. Every other `Deploy` caller writes `UpdateTileStatus running|error` afterwards (`web/db/handler.go:252-258`, `api/databases.go:250-255`, `apply.go:1228-1231`, `orgconf.go:977-980`, `volmove.go:675-680`). `volmove.go:667-672` documents that `managedtiles.Deploy` deliberately does not write status and the caller must. The watcher is the caller that forgot.

F8. [B] Backup restore recovery stops a service with no status write. `backup/work.go:171-172` → `stopFor` → `quiesce` `backup.go:404-417` scales the service down and leaves it. Web stop `app/handler.go:335-341` scales and writes `stopped` and nudges. The card shows `running` until the metrics reconciler `reconcile.go:107` notices on its next 30s tick, and the reconciler never touches a managed tile that has no `LabelDB` container listed on this node except through `RunningTileTasks` (`:93`). The same gap exists during a normal backup run: `quiesce` stops, the reconciler writes `stopped`, the deferred `ScaleService 1` restarts, the reconciler writes `running`; two status flips per backup that nobody asked for.

F9. [A] Tile status has fourteen writers and one observer. Rowed in W1. The reconciler `reconcile.go:24-68` is the only place that encodes "which kinds own a long-lived container" (`runpolicy.For(kind).KeepAlive`) for status purposes, while the handler writers (`app/handler.go:338`, `lifecycle.go:39`) write `stopped` for any kind. A cron marked `stopped` by web `Stop` stays `stopped` for ever because the reconciler skips it (`:26`), and `LoadSchedules` `jobs.go:311` only skips `paused`, so it still ticks.

F10. [A] Agent service ensure has two entry policies. Boot `main.go:463-484`: only when the swarm already has 2+ nodes, retried 10 times. Handler `web/server/nodes.go:71`: always on AddNode, once. A first-node install whose AddNode `Ensure` fails (registry not up yet, the exact case the boot retry exists for, `main.go:469-470`) gets no retry until the next boot with 2+ nodes.

F11. [svc] Boot-only steps that already look like services: `netpool.Backfill/Sweep` (store + runtime, `netpool.go:212-259`), `nodes.Sync` (store + runtime, also called from a GET handler `nodes.go:32` and so writes `servers` rows on page load), `registry.EnsureManaged` (store + runtime, two callers), `seedInstall` (store + proxy, one caller). None have a handler-vs-worker rule split beyond F2, F4, F10.

F12. [recorded] `SweepStaleRuns` and `workqueue.recover` both run before `srv.Start` (`main.go:315,549`), so handlers cannot race them. `agent.Ensure`, `EnsureManaged`, `EnsureTraefik+Resync` and `CheckUpgrade` run in goroutines (`main.go:285,361,463,488`) and can overlap the first requests; `SetRegistryDomain` `settings/handler.go:620` calling `EnsureManaged` while the boot goroutine is mid-`EnsureService` is not guarded (not checked whether `EnsureService` is idempotent under concurrency).

## 3. Service implications

Mapping onto `02-findings.md` section 2:

- 2.3 TileService + TileLifecycleService: W1, W19, F7, F8, F9. The lifecycle service is the natural single owner of `UpdateTileStatus`; the reconciler (W1) becomes a caller of `TileLifecycleService.Observe(tile, containerState)` rather than a second rule set. `quiesce` (W14) and `stopFor` (W15) call `Stop/Start` on it instead of the cluster directly. B3 (legacy mount conversion) is a `VolumeService.Create` caller (2.9).
- 2.4 DeployService: W5 (auto-update goes through `DeployService.Deploy` and inherits the upper-env rule), W9/W10 (cigate `Release`/`Fail` stay engine methods behind it), B9 (`SweepStaleRuns` becomes `DeployService.RecoverInterrupted`, one terminal-status vocabulary with `Cancel`). W20 recorded: deploy does not write the proxy, so ProxyService (2.6) is called by TileService/DomainService, never by the engine.
- 2.1 ManagedInstanceService: W6, W16. `Deploy(ctx, t)` writes status itself, closing F7 and the five copies in W16.
- 2.6 ProxyService: B7/F2 (`Resync` renders the registry route too, or `EnsureRegistryRoute` is a method called from boot and both handlers), B11/F4 (`SetTrustedProxies(cidrs, trustCF)` with one validation policy, called from seed and the handler), B12 (boot is just another `Ensure` caller).
- 2.8 RegistryAdminService: B7, B14 GC, F2. `EnsureManaged` gets one caller policy; the nightly GC becomes a method the maintenance page could also call.
- 2.10 BackupScheduleService + BackupRunService: W13, W14, W15; the run service owns quiesce and its status side effect via TileLifecycleService.
- 2.11 NodeService + AdminService + SettingsService: B18/F10 (`NodeService.EnsureAgent` with one retry policy, called from boot and AddNode), B19, B20/W18 (`Sync` stops being called from a GET; the ticker owns the write, the page reads), B14 cleanup flag, W3 interval setting.
- 2.12 SchedulerService: B16, W11, W13 (the two cron tables), plus `workqueue` (B23, W21) as the durable side; recovery semantics (F3 second half) live here.
- 2.13 NotificationService: W6/W15 missing nudges (already the shape of 2.13's B list).

New service the workers imply, not in 02-findings section 2: an **ImageWatchService** (W3-W8, F5, F6, F7) that owns `image_digest`/`latest_digest` baselining for all three writers (engine OnFinish, managed Deploy, watcher), the check-history rows, and calls DeployService / ManagedInstanceService for the auto branch.
