## 2. Findings

- **F1. Raw container Stop vs Remove guard, no class (single surface).** `Stop` refuses any system-labelled container regardless of state (web container 212), `Remove` refuses only a running one and re-inspects to decide (224-235), `Start` and `TermWS` have no guard (202, terminal.go:36). The rule "the panel, proxy, agent and registry are not stoppable from the UI" is handler code; `cluster.StopContainer` / `StopRemove` (`infra/cluster/cluster.go:171,182`) accept anything, which `envnet.TearDown` relies on (`envnet.go:214`). No API or CLI container routes exist (`handlers/api/v1/v1.go` has none), so there is no twin to drift against today.
- **F2. CLI approve evaluates write scopes against the browser's active org.** `web cli` 55 and 96 read `stackrmw.CanWrite(c)`, which is the role in the org the session cookie points at (`handlers/middleware/orgctx.go:132-138`). The minted key is user scoped, not org scoped (`repo.APIKey` has `UserID`, `web cli` 156), and `api/auth.go` checks org membership per request (1.8 "Org access" row). A user who is writer in org A and reader in org B mints a write key while A is active; whether that key can write in B depends on the API's per-request check, not on this filter. Not runtime-verified. Same shape in `web account` 201.
- **F3. Root domain rules, class A (installer vs web).** Installer `CheckRoot` (`answers.go:518-549`) refuses an IP, `localhost`, a single label, a numeric TLD, labels over 63 chars and leading or trailing dashes. The server stores the same value as the instance domain resource with only `ToLower` + `TrimSpace` + `HostTaken` (`cmd/stackrd/seed.go:33-46`), and the web path for domain resources is `envops.ValidateResourceHost` (`config/envops/envops.go:287-299`: lowercase, no scheme, slash, port or space). So `localhost` or `intranet` is refused by the installer and accepted by the panel. `proxy.routablePanel` (`infra/proxy/proxy.go:797-802`) separately refuses IP and `localhost` for the panel host only. Three rule sets for "is this a domain we can serve".
- **F4. Panel service spec owned by the installer alone.** `serviceArgs` (`steps.go:128-169`) is the only place the env list (`BASE_URL`, `ACME_EMAIL`, `STACKR_TLS`, `ROOT_DOMAIN`, `TRUST_CLOUDFLARE`, `TRUSTED_PROXY_CIDRS`, `DATA_DIR`, `DATABASE_PATH`, `TRAEFIK_HTTP_PORT`, `TRAEFIK_HTTPS_PORT`, `HOST_PROC`, `STACKR_IMAGE`), mounts and constraints are defined in Go. `scripts/dev/deploy-test.sh:118-131` is a hand copy (adds `--publish mode=host,published=8080`, reads env from a file). `AdminService.Upgrade` changes image and `STACKR_IMAGE` only (`service/admin.go:156`), so an env var the server starts needing reaches fresh installs but never upgraded ones. Matching values checked: network `stkr` (`steps.go:131,337` = `runtime.go:46`), hostname `stkr-panel` (132 = `runtime.go:49`), relay tag `stkr-proxyrelay:local` (21 = `runtime.go:80`, `admin.go:145`), registry port default `5000` (278-281 = `cmd/stackrd/main.go:84`), service name `stackr` (130 = `admin.go:33`), swarm label (363 = `runtime.go:1341`), ports 80/443 (`flags.go:36` = `main.go:341-342`), `STACKR_TLS` off spelling (136-138 = `main.go:83`), `TRUST_CLOUDFLARE` "1" (141 = `seed.go:65`), CIDR list comma-joined (`answers.go:578` = `seed.go:47`). Diverging defaults: `DATA_DIR` `/var/lib/stackr` (`flags.go:77`) vs server `./data` (`main.go:79`), `DATABASE_PATH` `<data>/stackr.db` (156) vs `./data/stackr.db` (75), both harmless because the installer always sets them. The wrapper execs `/app/stackr` (363), present in `cmd/stackrd/Dockerfile:48` but not in `Dockerfile.runtime:6-10`, so the wrapper is dead on a rig built from the runtime image. Server also reads `TRUSTED_PROXIES` (`main.go:78,143`), a second name the installer never sets; relation to `TRUSTED_PROXY_CIDRS` not checked.
- **F5. Relay port defined twice.** `cmd/proxyrelay/main.go:107` defaults `-listen :15000`; `runtime.ProxyRelayPort = 15000` (`runtime.go:83`) is what the server dials (`runtime.go:362`), and the server passes only `-target` (`runtime.go:360`). Both say 15000 today; nothing ties them. Idle 60s is relay-only (`main.go:109`); the server's comment relies on it (`runtime.go:388-390`).
- **F6. Pending-moves filter copied.** `web/project/handler.go:978-989` and `config/stackconf/apply.go:1929-1943` both drop a plan's move blocks when `placement.InGroup` says the data is already in the wanted group. Same predicate; the web copy additionally maps `FromNode` to a server name (983-985). Same result today, duplication only.
- **F7. Notification center GET writes.** `web notification` 35 marks everything read on page render and drops the error. Single surface, recorded as handler side effect that moves.
- **F8. CLI exchange is a third API-key minting site.** `web cli` 153-161 beside `web account` 214-222 (1.8 already lists two); the scope filter is a second copy (96-104 vs 201-209) and does not call the `CanGrantWrite` helper exported for it (`web account` 258-262). No API or CLI surface can list or revoke keys (`handlers/api/v1/v1.go` registers none).
- Agreement recorded, no class: installer `CheckProxies` and the boot seed and the Proxy page all use `netaddr.ParseTrusted`; `envnet.UpperEnv` applies the same deploy rule on api and web; graph builders and `annotate` carry no rule of their own.
