## 2. Candidate services

- **BackupScheduleService** (`internal/stackrd/service/backupsched` or beside `infra/backup`)
  - `Create(ctx, tile *repo.Tile, spec ScheduleSpec) (*repo.Backup, error)` — spec = destRef (id or `${{ }}`), kind (derived unless explicitly volume on a managed tile), mode, cron, tz, keep, enabled. Owns: org lookup (`authz:34`), dest resolution (`authz:19,77,114`), kind derivation, `VolumeFor` check, mode-on-dump rule, `Validate`, store write, scheduler reload.
  - `Update(ctx, b *repo.Backup, spec ScheduleSpec) error` — full struct in, same checks, reload.
  - `Delete(ctx, id string) error` and `DropForTile(ctx, tileID string) error` — reload after; the latter is what every tile-delete path should call.
  - `ListByTile(ctx, tileID) ([]repo.Backup, error)`, `Reload(ctx) error` (wraps `eng:83`).
  - Calls: BackupDestinationService.Resolve, TileService (org of tile, `VolumeFor`), ManagedGate (editGate/rejectManaged decision for file-owned `backup:`), infra/backup scheduler.
  - Call sites: `web/bk:189,242,280`, `api:154,230,288`, `conf:178`, plus the six `DeleteTile` callers.

## 3. Drift findings

- **Create destination — A.** Web trims `name/endpoint/region/bucket` (`web/set:304-308`); API stores them untrimmed (`api:58-61`), so `ResolveNamed` (`authz:85`) can miss a name with a stray space created over the CLI. Web org route passes through `RequireOrgSetup` (`orgctx.go:183-186` via `web/set:160`); API `requireOrgWrite` (`auth.go:300-309`) has no setup-done check, unlike every tile route (`auth.go:292`).
- **Delete destination — B.** `backups.destination_id REFERENCES backup_destinations ON DELETE CASCADE` (`001_initial.up.sql:52`) removes every schedule on the destination. Neither `web/set:336-357` nor `api:84-104` calls `LoadSchedules`; the in-memory cron entries (`eng:61`) survive and fire `Start` on rows that no longer exist (`eng:100-102`, `work:109-112`) until the next unrelated reload. Same on both surfaces, so not one-surface drift, but a live missing effect.
- **Create schedule — A (four divergences).**
  1. Kind: web forces dump on managed unless form `kind=volume` (`web/bk:217-219`); API takes any body kind, default by `IsManaged` (`api:181-187`), and accepts `dump` on a non-managed tile, which `Validate` (`authz:50-54`) passes and `writeDump` (`eng:318-320`) fails at run time; config derives kind and cannot express a volume backup of a managed tile (`conf:39-44`).
  2. `VolumeFor` guard: web `web/bk:223-228`, API `api:197-201`; config `applyBackups` has none (`conf:217-230`), so a `backup:` block on a service tile writes a row that fails every tick (`eng:285-288`).
  3. `Validate` not called on the config path (`conf:217-235`); it relies on parse-time `validateBackup` (`stackconf.go:934-970`), a second implementation of the same rule set (tz via `time.LoadLocation` `stackconf.go:950` vs `CRON_TZ=` prefix through `cron.ParseStandard` `models.go:915`, `jobs.go:65`). Config additionally makes `mode:` on a managed tile an error (`stackconf.go:961-964`); web/API store it silently.
  4. Default `keep`: web 7 (`web/bk:213`), API/CLI/config 0 = keep all (`api:178`, `cli:164`, `conf:220`, `eng:603`).
  Also: no `editGate`/`rejectManaged` on web (`web/bk:189-239`) or API (`api:154-210`) although `backup:` is a file-owned key (`conf:3-8`, `apply.go:983`); the next apply deletes any UI-created schedule on a tile the file does not declare (`conf:209-215`). The web comment justifying the missing gate is stale (`web/bk:314-317`, "backups are not expressible in the config file at all").
- **Update schedule — A.** Web overwrites `cron` and `timezone` from the form (`web/bk:262-263`), so a tz can be cleared; API patches only non-empty fields (`api:266-271`), so `stackr backup set --tz ""` is a no-op (`cli:181-187` drops empty values too). Config updates `cur[0]` only (`conf:232-235`) while the plan diff compares `cur[0]` only (`conf:119`): a second schedule added in the panel is invisible to `plan` and deleted by `apply` when the block is dropped (`conf:209-215`).
- **Delete schedule — B.** Explicit deletes reload (`web/bk:288`, `api:297`, `apply.go:988`). Tile deletes cascade the rows (`001_initial.up.sql:51`) from `api/v1/helpers.go:134`, `web/handler/app/handler.go:1640`, `web/handler/db/handler.go:467`, `stackconf/apply.go:1566`, `orgconf/orgconf.go:952,992` with no backup-scheduler reload on any of them (only `jobs.LoadSchedules` is called in those files). Same orphan-entry behaviour as the destination case.
- **Share / unshare — no class, duplication.** `destinationUsers` is copied verbatim (`web/set:712-738`, `api:451-480`), including the "add a store query" comment.
- **Run now — no class, robustness.** API returns 503 on a nil service (`api:334-336`); web dereferences `h.svc` (`web/bk:299`) while its own `reload` guards nil (`web/bk:328`). `Start` itself guards a nil queue (`work:106-108`) but not a nil receiver.
- **Panel self-backup — parity, not drift.** Create is web-only (`web/set:216`, `api:188` refuses); patch/run/delete reach the row over the API by id (`api:124-130`) but nothing lists it, so the CLI cannot discover it (`docs/surface-parity.md:36`).
