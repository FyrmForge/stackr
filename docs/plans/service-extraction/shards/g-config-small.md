## 2. Findings

1. Org rename, A. `web/org/members.go:101-116` refuses a slug that another org's domain host leads with; `O:424-441` (plan) and `O:660-673` (apply) check only collision and registry images. An org file can take a slug the panel refuses.
2. Org domain resource, A and B. Web create runs `envops.CheckOrgSquat` (`web/org/settings.go:547`); `O:461-482` and `O:811-823` do not, and neither does `api/domainresources.go:100-135`. Web creates `Declared=false` with no `ACMEEmail`; orgconf creates `Declared=true` with the file's acme address. Changing `acme_email` through the API rewrites the resolver set (`api/domainresources.go:224-227`, `px.EnsureTraefik`); `applyDomains` `O:826-833` writes the row and calls nothing, while its plan note promises a traefik restart (`O:477`).
3. Org var names, A. Web accepts `varNameRe` only (`web/org/settings.go:411,422`); api `writeVars` accepts any non-empty name (`api/variables.go:120`); orgconf applies any `vars:` key (`O:706-712`) and `Parse` never checks them.
4. Settings write gate, A. Only web org defaults refuses a panel write on a config-managed owner (`web/org/registry.go:262-265`). `api/settings.go:44-75` writes org, stack and env rungs with no managed check; `web/project/handler.go:1022` and `:2540` write stack and env rungs the same way. The next apply overwrites them (`apply.go:931-937`, `O:687-691`) with no plan row saying so.
5. Org share create, B. `api/storage.go:117-135` probes the share on create and records status; `orgconf/storage.go:213-217` inserts `Status:"unknown"` and nothing probes it until a tile mounts it. Orgconf is also the only surface with an update path (`storage.go:223-233`).
6. Stack binding from the org file, A and B. `web/project/handler.go:718-721` refuses a connector outside the stack's org and `:735-741` drops staged rows when the file takes over; `O:895-902` writes `ref.Connector` as given (`refBinding :621-630`) and leaves staged rows in place. Repo normalisation (`:727`) is also missing, so `https://github.com/o/r.git` in the file and `o/r` in the panel are different bindings.
7. Org-shared instance, A. `api/databases.go:228-233` refuses reserved slugs and slug collisions in the env; `O:962-970` creates in `hostEnv` with neither check. `api/databases.go:423-432` refuses deletion while provisions are held unless `force=true`; `O:985-995` removes the instance and its row outright. The teardown calls differ (`api/helpers.go:129-135` vs `managedtiles.go:570-577`); equivalence not checked.
8. Inline stacks are never deleted. `O:609` and `O:768` skip stacks without `ConfigManaged()`; an inline stack has no `ConfigRepo` (`O:862-870`), so removing it from the file plans nothing. Not checked whether intended.
9. Web create tile bypasses runpolicy, A. `web/project/handler.go:492-503` switches on three literals and defaults anything else to `service`; `:570` writes `container_port` for any kind. `api/apps.go:103,122` rejects both. `web/prhook/handler.go:388,684` deploys `service` and `cron` on push and skips `function`; no `Policy` field expresses that.
10. Webhook token entropy, A (minor). `O:966` and `api/databases.go:237` mint `WebhookToken` with `uuid.New()`; web tiles use `secrets.RandomHex(24)` (`web/project/handler.go:576,1693`).
11. Plaintext credentials at rest. Encryption happens only in `store/repo/sqlite` for tile env, variables, provisions, backup secret keys, storage passwords, cert keys and drop-link values. `registries.password` (`sqlite/infra.go:31-51`), `Tile.DBPassword`, `Tile.BasicAuthPassword`, `Tile.WebhookToken` and `Settings.ProtectPassword` are stored as written. Every writer of those fields is a handler or infra package; none routes through `secrets`.
12. KEY=VALUE parsing has three inline copies (`plan.go:1126-1132`, `deploy/engine.go:1298`, `api/helpers.go:145-159`) beside `envutil.Parse`; the api writer emits unquoted lines the package reader would split on a quoted newline. Whether multi-line values reach those paths is not checked.

## 3. Service implications

- `OrgPlanService` (`02-findings.md 2.5`) takes `orgconf.Runner` whole. Its apply steps map onto other services and today re-implement them: rename to `OrgService` (finding 1), domains to `DomainResourceService` (2), vars to `VariableService` (3), defaults to `SettingsService` (4), storage to `StorageService` (5), binding to `StackService` or `PlanService` (6), shared instances to `ManagedInstanceService` (7), stack delete to `StackService`. Every A or B above is a place where orgconf and a handler each hand-build what the same service method would do once.
- `SettingsService` (`2.11`): `settings.Merge`, `Check`, the store write and `PX.Resync` are already one sequence copied at seven sites; the managed gate (finding 4) is the one rule not yet shared. `settings.Resolve` and the `For*` readers stay a pure helper under it.
- `secrets` stays a pure helper. The service-level question is finding 11: which service owns each plaintext credential field (registry admin, managed instance, tile, settings) and whether it encrypts before the store.
- `runpolicy` stays the kind registry, consumed by `TileService` (`2.3`); finding 9 is the web create path that must route through it. The service-only knob rule (`api/apps.go:332-361`, `stackconf.go:1021`) is a candidate `Policy` field so it stops living in two places.
- `varref` stays a pure helper under `VariableService` (`2.2`). `envutil` and `envcolor` stay pure helpers; the inline parsers in finding 12 are cleanup, not a service boundary.
- `sharelink` seeds `ShareLinkService` (`2.2`); the mint validation in `web/project/handler.go:2351-2390` is the logic that moves into it. `envcompare` seeds `EnvCompareService` (`2.2`) unchanged.
