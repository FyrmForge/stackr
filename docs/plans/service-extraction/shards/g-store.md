## 2. Findings

- **Tile delete, provisions (B).** `DeleteTile` covers `variables` and `resource_bindings` (`tiles:269-282`) and the FK cascade covers domains, deployments, backups. `provisions` has no FK (`sql:199-213`). Web (`web/app:1635-1639`) and config (`apply:1559-1565`) detach consumed slices before the row goes; the API `teardownTile` (`api/helpers:129-135`) and orgconf (`orgconf:952,992`) do not, so an API tile delete leaves provision rows pointing at a dead consumer.
- **Env delete leaves staged edits and canvas layout (B, all surfaces).** `staged_changes` has no FK (`sql:271-281`) and `node_positions` has none. `envops:511-584` cleans variables and provisions but neither of those; `DeleteEnvironment` is a bare row delete (`stacks:378-381`). The stack path cleans env canvases (`stacks:276-282`), the env path does not, so `env:<id>` rows outlive the env and a stale pending set survives until the next `DeleteStagedByEnv` caller happens to run (`web/proj:738`).
- **Email case (A).** `users.email` is UNIQUE and case-sensitive (`sql:341`); the store does not fold case (`users:559-578`). Register, login, invite and both member flows lowercase (`register/handler.go:67`, `login/handler.go:58`, `invite/handler.go:74`, `api/members:70`, `web/orgmem:244`); the profile email change does not (`web/acct:78-88`). Saving `Bob@X` there stores mixed case; the next login lowercases and `GetUserByEmail` misses.
- **Env slug `stack` (A).** The home env is a real row with slug `stack` (`repo/models.go:192-195`, `stacks:159-163`) hidden by `ListEnvironmentsByStack` (`stacks:302-306`). API refuses the slug (`api/envs:132`); web refuses only `settings` and `list` (`web/proj:323`) and has no dup pre-check, so a web env named "Stack" hits `UNIQUE (stack_id, slug)` (`sql:126`) as a raw 500.
- **Stack create dup (A).** Renames pre-check `UNIQUE (org_id, slug)` (`api/lifecycle:359`, `runner.go:424`); creates do not (`api/stacks:39-41`, `web/proj:161-169`). No surface maps SQLite constraint errors, so the second "My App" stack is a 500 on web and API and a looked-up no-op in config (`orgconf:855-864`).
- **Dead tile defaults (A).** `CreateTile` writes every column (`tiles:43-58`), so the SQL defaults for git_branch, dockerfile, build_context, timeout_minutes (`sql:292-295,316`) never apply. Each surface re-supplies them: web unconditionally (`web/proj:568,574-575`), API only for schedule kinds and only dockerfile/context (`api/apps:118-120,137-144`), config via `defStr` (`apply:1902-1904`) and 30 for cron/function (`apply:1206-1208`). The store itself defaults only scope_kind, replicas, endpoint_protocol, update_policy (`tiles:30-42`): one rule set split across four places.
- **Domain https default (A).** SQL default is on (`sql:107,114`) but dead (`dom:83-90`). API defaults on/on (`api/domains:54-63`); the web form's unchecked checkbox writes off/off (`web/app:1738,1742`, `web/db:602`). Same `POST` shape, opposite default.
- **Domain host+path rule (A).** Store uniqueness is `(host, path, rule)` (`sql:370`) and `GetDomainByHostPath` returns the plain row first (`dom:118-120`). `web/app:1700` mirrors the index (same tile may add a rule row); `api/domains:70` and `web/db:593` refuse any existing row, stricter than the store.
- **Unaudited secret writes (B, config and infra surfaces).** Every web and API secret set/delete records an audit row (table above). Config apply mints generated secrets with none (`apply:1802-1816`, `orgconf:723-727`), env clone copies secret rows with none (`envops:219-231`), env teardown deletes per-PR secrets with none (`envops:548-553`), managed tiles publish connection secrets with none (`infra/managedtiles/managedtiles.go:383-389`, `provision_s3.go:177-178`). The audit trail shows who read a secret but not that the config engine created or rotated it.
- **Shared instance slug not slugified.** `orgconf:962-966` writes `Slug: name` from the file key while every other tile create passes `repo.Slugify` (`api/apps:80`, `web/proj:481`). A key with a capital or space is a slug no URL or `${{ tile.<slug> }}` reference can spell.
- **Three copies of the default env.** `CreateStack` already inserts the home (`stacks:144-166`); `api/stacks:44-47`, `web/proj:172-182`, `orgconf:867-869` each add an identical `production` row.
- **Backup destination secret rule is dormant.** `bk:46-62` keeps the stored key when `SecretKey == ""`, but both callers pass the decrypted row (`web/set:682-697`, `api/backups:441`), so nothing exercises it. If a service later sends a sparse struct the rule fires; note it exists.
- **Deployments have no claim.** Work items move by rows-affected (`work:67-76`); deployments are read then written in Go (`infra/deploy/engine.go:124-128,310,456`), the same status machine in two styles.

## 3. Service implications

- A service that deletes a tile does not delete domains, deployments, backups or runs: the FK cascade does (`sql:103,91,51,40`), and `DeleteTile` already drops variables and bindings (`tiles:269-282`). It must detach provisions (`web/app:1635-1639`) and reload the backup scheduler (shards/backups.md) because nothing below does.
- A service that deletes an environment must clear `staged_changes` and the env `node_positions` itself (nothing does today), plus the variable and provision cleanup `envops:511-584` already does. Stack and org deletes get node_positions from the store (`stacks:107-133,271-285`) but not staged changes, variables, secret links, domain resources or plans.
- Slug and email normalisation belong in the service, not the store: the store stores whatever it is given (`stacks:43-48`, `users:571-578`). One `Slugify` and one `ToLower` at the service edge replaces 30 and 8 call sites and fixes `web/acct:78-88` and `orgconf:963`.
- Constraint errors need mapping once. No layer today turns a SQLite UNIQUE failure into a conflict; a service can either keep the pre-check lookups (`api/apps:84` style) or catch the error, but it decides once for web, API and config.
- Defaults for a new tile, domain or backup are a service concern, not SQL: `CreateTile`, `CreateDomain`, `CreateBackup` write every column so the `DEFAULT` clauses are inert (`tiles:43-58`, `dom:83-90`, `bk:71-75`). The store keeps only scope_kind, replicas, endpoint_protocol, update_policy (`tiles:30-42`) and `storage.server_id = local` (`stor:24-26`).
- The store already owns: encryption at rest, `UpdateTile` field exclusion (status, slug, home_node, shared_net, digests, `tiles:160-217`), path normalisation for domains (`dom:76-81`), home env creation and hiding (`stacks:144-166,302-306`), plan superseding (`stacks:264-269`), atomic claims for work items, secret links and join keys, and the canvas caps. A service calls these and must not re-implement them; in particular it must not insert a second home env or set `t.Slug` and expect `UpdateTile` to persist it.
- Audit writes stay a caller duty (`audit:185-190`); a VariableService must record `Set`/`Delete` on every path, which today means adding it to config apply, env clone and teardown, and managed tile publication.
- `projectEnvVars` runs inside `CreateTile`/`UpdateTile` (`tiles:62,216`); a service writing structured variables must know the blob write will re-add anything the blob still names (`infra/managedtiles/resources.go:177-181`).
