## 3. Drift findings (one per flagged row)

**Row 1 — A.** Target rule differs three ways. Web `project/handler.go:537` requires `target.Kind=="service" && !IsManaged`; API `volumes.go:44` only refuses a managed or volume *app*, so a cron can own a volume; config `apply.go:1383` accepts any tile slug and then `redeployAttached` (`:1397`) silently skips a non-service target. Web can create a detached volume (531-545, attach optional); API cannot (app in URL). API takes `volume_name`/`max_size_mb` (`volumes.go:56,70`); web form does not (grep). Write mode differs: web always stages for a UI stack (`:586-598`), API writes and enqueues immediately (`:77-80`).

**Row 2 — B.** Re-attaching a volume from service A to B. Web `app/handler.go:794-801` enqueues both A and B. Config `apply.go:1393-1399` deploys only the new `vol.AttachedTileID`; A keeps the old bind until something else redeploys it. Same operation through a plan leaves a stale mount the UI path does not.

**Row 3 — A.** `max_size_mb` and `volume_name` exist only at API create (`volumes.go:56,72`) and web attach (`handler.go:765`, size only). No patch key, no `TileConf` field, `applyTileConf` `apply.go:1683-1686` never writes them; a web staged create (`project/handler.go:587` via `TileConfOf`) cannot carry them. Field set differs per surface, same field-list problem as calibration "Tile field lists".

**Row 4 — B.** `DELETE /apps/:id` with a volume tile id (`apps.go:463`, `requireTile` `auth.go:313` has no kind check) runs `teardownTile` and returns; the attached service is not enqueued, unlike `deleteVolume` `volumes.go:104-107`. The running service keeps a bind to a volume with no row. Also A: web `handler.go:1616` refuses deleting an attached volume; neither API path does.

**Row 12 — A.** API `storage.go:100` hard-codes `ServerID: "local"`; web `storage.go:80` uses the page's `:id`. `NodeOfStorage` (probe, path volumes, `ensureForConsumer`) therefore lands on the manager for every CLI-created pool; a local pool on a worker is web-only. Config org shares are created with `Status:"unknown"` and never probed (`orgconf/storage.go:213-217`), while web/API probe on create.

**Row 14 — B.** Web `server/storage.go:105-125` has no `OrgID` branch: an org share row posted to it is deleted via the declared-path loop, skipping `DropOrgShareVolumes` (`api/storage.go:266`) and the config-managed-org refusal (`orgShareOwner` `:238`); its consumer scan (47-65) parses `slug/path` lines only and cannot see `${{ org.storage.NAME }}` references (api uses `varref.OrgStorageRef` at 264). Whether the server page exposes org rows to this form: not checked.

**Row 15 — A.** Web `storage.go:150-152` slugifies then rejects empty; API `storage.go:185,189` rejects empty raw name then slugifies, so a name of only punctuation yields a path with `Name==""`.

**Row 17 — A.** Config refuses `storage:` on anything but a service (`stackconf.go:1064-1066`). API writes `t.Storage` for any kind (`apps.go:297-321` sits before the `t.Kind=="service"` block at 332); web `app/storage.go:71` has no kind check. A cron with storage attached over API/web is a row the config planner will reject on export. Gate differs too: web uses reject-only `RequireUnmanaged` (78) where the rest of the tile's field edits use `editGate`; a `ui_edits: stage` stack stages a settings save and 409s a storage attach. Web cannot attach org shares at all (`GetStorageBySlug` 91 only; `storageOptions` 32-58 lists no org rows because they have no declared paths).

**Rows 9-11 — C.** Calibration finding, extended: `DeleteVolume` `server/handler.go:277-308` confirms only against the live `docker volume ls` (292-301); nothing consults rows, so `stackr-db-<id8>`, `stackr-vol-<id8>` and adopted `VolumeName` volumes with live tiles are deletable. Needs `VolumeOwnership.OwnerOf` before any guard can exist.
