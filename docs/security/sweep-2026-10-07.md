## Real findings

### F1 High: OpenSSL in the runtime image
Image `ghcr.io/fyrmforge/stackr:0.6.0-dev.15` (base alpine 3.21.7): libcrypto3 and libssl3 3.3.7-r0 carry
CVE-2026-45447 (fixed 3.3.7-r1), CVE-2026-75804 and CVE-2026-84782 (fixed 3.3.7-r2). Risk: TLS/crypto flaws in
every process in the image that links OpenSSL (stackrd itself is Go, so exposure is the helper binaries).
Fix: rebuild the image (Dockerfile base pull, or `apk upgrade --no-cache`) so r2 lands; re-run trivy image.
In-flight: none, Dockerfile is not under blitz edit.

### F2 High: google.golang.org/grpc v1.83.1 (CVE-2026-84445)
`go.mod:240`, indirect. Fixed in 1.83.2 / 1.85. Not flagged reachable by govulncheck, but ships in the binary.
Fix: `go get google.golang.org/grpc@v1.83.2` (or newer) then `go mod tidy`. Also bump
`otlptracegrpc` to v1.45.0 and `otlploggrpc`/`sdk/log` to v0.21.0 (F6) in the same pass.

### F3 High: github.com/docker/docker v28.5.2+incompatible
`go.mod:18`, direct. CVE-2026-41567, CVE-2026-42306 (trivy HIGH), GO-2026-4887 and GO-2026-4883 (govulncheck,
reachable by call graph through `internal/service/internal/docker/*`). All four have no fixed version upstream.
Risk is on the daemon side (AuthZ plugin bypass, plugin privilege validation, malicious image decompression,
host file overwrite race); stackr only uses the client SDK and does not install plugins or run an AuthZ plugin,
so exposure comes from the Docker engine, not this module. Fix sketch: keep engine patched on the rig/prod hosts;
watch for the `moby/moby/client` module split and move to it when a fixed release exists. Accepted until then.
In-flight: `internal/service/internal/docker/*` and `jobs.go`/`orchestrator.go` are under blitz edit; no change needed.

### F4 Medium: github.com/prometheus/prometheus v0.303.0 (indirect, `go.mod:157`)
GO-2026-5710, 5662, 5381, 5264, CVE-2026-42151, CVE-2026-42154 (the last two HIGH in trivy). govulncheck marks
them reachable by symbol, but they concern the Prometheus server (web UI XSS, remote read DoS, remote write
OAuth secret) which stackr does not serve; the module is pulled by the hamr dependency. Fix: bump to v0.311.3
via `go get github.com/prometheus/prometheus@v0.311.3`, or drop the dependency in hamr. Low practical risk.

### F5 Medium: golang.org/x/mod v0.39.0 (`go.mod:32`)
CVE-2026-56864, CVE-2026-56865 (HIGH in trivy). Build-time module parsing library; not on a request path.
Fix: `go get golang.org/x/mod@v0.40.0`.

### F6 Low: OpenTelemetry exporters
GO-2026-6615 (sdk/log busy-spin), GO-2026-6508 (log gRPC exporter ignores env TLS certs), GO-2026-6505 (endpoint
URLs in info logs). All indirect (`go.mod:204,209`). Only matters if OTLP export is configured. Fix with F2.

### F7 Low: golang.org/x/crypto v0.55.0, GO-2026-5932
Trivy UNKNOWN severity, no fixed version listed. Re-check on the next sweep.

### F8 Low: alpine MEDIUM/LOW in the image
41 MEDIUM and LOW OS findings; cleared by the same rebuild as F1.

### F9 Info: `data/registry/token.key` is a live private key on disk
Flagged by gitleaks (tree) and trivy secret scan. Gitignored (`.gitignore:25 data/`), never in git history
(`git log --all` empty for the path), so not a leak; it is the local dev registry token signing key. Only
relevant if the working tree is copied elsewhere. Fix sketch: none needed; keep `data/` excluded from any
image build context (`.dockerignore`).
